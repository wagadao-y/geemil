# Spatial Hub 設計メモ

施設の 3D データ（メッシュ・点群・3D Gaussian Splatting）と 360°写真を施設ローカル座標で重ね、場所に紐づく情報（注記・関連リンク・添付ファイル）への入口にするアプリの設計判断をまとめる。点検記録や文書そのものは持たず、既存システムへのリンクで接続する。アプリの役割は現実空間の可視化で、空間のどの位置に何（設備など）があるかを示すこと。対応の要否や進み具合の管理は、設備管理システムや点検記録の管理システムが担い、関連リンクで紐づける。UI のプロトタイプは [apps/web](../apps/web/README.md) にある。

## 構成

- フロントエンド：SvelteKit（`adapter-static` の SPA）
- バックエンド：Go のシングルバイナリ（API とフロントエンドの配信）
- データベース：SQLite から始め、PostgreSQL にも対応する
- ファイル：ストレージに置く。ローカルディスクから始め、S3 / R2 などのオブジェクトストレージにも対応する

## テナント

- テナントが持つすべての行に `tenant_id` を持たせる。自社だけで動かす OSS 版も、既定のテナントを 1 つ自動で作って同じ構造で動かす。後から SaaS にするときに作り直さないため。
- 分け方は、全テナントで同じスキーマを共有し `tenant_id` 列で区別する。SQLite でも PostgreSQL でも同じ形で動く。テナントごとのスキーマや DB ファイルは、マイグレーションの手間に見合わないので採らない。
- 絞り込みはリポジトリ層ですべてのクエリに必ず入れる。PostgreSQL では行レベルセキュリティ（RLS）も重ね、書き忘れの防御にする。
- ID はテナントをまたいで一意な UUIDv7 などにする。テナントごとの連番は件数が URL から推測でき、データの移行や統合もしにくい。
- ストレージのキーは `tenants/{tenantId}/...` から始め、テナント単位の削除・書き出し・アクセス方針を扱えるようにする。
- ユーザーは 1 つのテナントに属し、`users` に `tenant_id` を持つ。メールアドレスはテナントの中で一意にする。同じ人が複数の顧客にまたがる場合は、テナントごとに別のアカウントにする。
  - 顧客は自社の ID 基盤（SAML / OIDC）でログインさせたいことが多く、ID 基盤はテナントごとに決まるため。SSO 自体は後から対応する。
  - アカウントの発行・停止・監査を顧客側で完結できるため。
- 別のアカウントへの共有は後から次の形で足す。どちらも「データへのアクセスは、データを持つテナントの中で認可する」原則を崩さない。テナントをまたいで権限を直接付与する形は採らない。
  - 持ち主のテナントにゲストアカウントを発行する。見られるスペースと有効期限を絞り、ログインはメールのワンタイムリンクなどにする。
  - アカウントなしの共有リンク（閲覧専用・範囲限定・有効期限・取り消し可）。点群などのファイル取得もこのトークンで認可する。
- そのため、権限は「スペースに対する付与（誰に・どの範囲・いつまで）」として持ち、認可の判定は 1 か所にまとめる。後からゲストや共有リンクを判定の主体として足せるようにする。
- OSS 版ではテナントを UI に出さない。

## 権限

- 権限の木は「テナント → フォルダ → 施設 → スペース」とつながる。
- 権限は「誰に（ユーザーかグループ）・どのフォルダかスペースで・どの役割か」の付与として持ち、下へ継承する。フォルダやスペースごとに個別に設定する手間を省くため。施設が増えても、フォルダに付与すれば配下のすべての施設に効く。
- スペースに「制限付き」の印を付けると、上からの継承がそこで止まる。中を見られるのは、そのスペース以下で直接付与された人だけになる。
  - 単純な「拒否が勝つ」形にしないのは、「地下 1 階は全員に見せないが、関係者だけは見られる」とき、関係者も「全員」に含まれて拒否されてしまうため。
  - 制限付きスペースは、[セキュリティ](#セキュリティ)の「別ファイルに分けて配信のたびに認可する」範囲と対応する。
- 役割は次の 3 段階。別に、テナント内のすべての操作ができるテナント管理者（スーパーユーザー）を置く。
  - 閲覧：見る、コメントする
  - 編集：注記を作る・直す、写真の位置合わせ
  - 管理：アセットの登録、スペースの構成、権限の設定
- 権限のない人には、制限付きスペースの存在自体（名前・注記・写真）を返さない。

## 施設一覧とフォルダ

- 施設一覧は、テナントで共通のフォルダの木で整理する（例：本社 → 東日本支社 → 〇〇事業所 → 施設）。深さは任意。
- 施設は必ず 1 つのフォルダに属する。複数所属にしないのは、権限の継承を一意に決めるため。横断的な分類（発電種別など）が必要になったら、権限に関係しないタグを後から足す。
- フォルダの作成・移動と、施設をフォルダ間で移すことは、そのフォルダの管理の権限を持つ人に限る。施設を移すと見られる人が変わるため。
- 自分に権限のない施設しか入っていないフォルダは表示しない。
- テナントごとに明示的なルートフォルダを 1 つ持つ。ルートへの付与がテナント全体への付与になる。
- ログイン後の最初の画面はホームにし、お気に入り・最近開いた施設・自分が見られる場所を並べる。「自分が見られる場所」は、権限を持つフォルダや施設のうち一番上にあるもの。一部のフォルダだけ見られる人が、中身が空に見える上位のフォルダを辿らずに済むようにする。全体を見られる人ではルートの中身と同じになる。
- 権限のない上位のフォルダの名前は、パンくずにも出さない。組織の構造を見せたくない顧客があるため。
- 個人用には、お気に入り（ピン留め）と最近開いた施設を用意する。権限には関係しない。個人ごとのフォルダは、共有フォルダとの二重管理になるので作らない。
- 一覧表示のほかに、施設の原点を緯度経度に変換して地図上に並べる表示を用意する。名前・所在地での検索もできるようにする。

## 座標系

- アプリは日本国内に限定しない。前提は「単位がメートルの投影座標系」で、日本の平面直角座標系（JGD2011 の第 I〜XIX 系）はその一例として扱う。
- 施設ごとに次を持つ。
  - 座標系：投影座標系の EPSG コード（例：平面直角座標系 第 IX 系は 6677、UTM 54N は 32654）。基準を持たない「ローカルのみ」も選べる。
  - 原点：その座標系での X・Y と標高
  - 回転：座標北に対する施設ローカル座標の軸の回転（建屋の向きに軸をそろえたいとき）
  - ジオイド高：原点での値。3D Tiles の楕円体高と、点群などの標高とのずれ（日本では 30〜40 m）を補正する。施設の範囲ではほぼ一定なので 1 つで足りる。手で入れるか、国土地理院のジオイドモデルや EGM2008 から計算する。
- 施設ローカル座標（m、Z 上向き）は「投影座標 − 原点」を回転したもの。投影座標は 10 万 m 規模の値になり、そのまま GPU に渡すと精度が落ちるため、原点を引く。
- 座標変換が要るのは、3D Tiles（地心座標系）から施設座標への変換と、施設一覧の地図に出す緯度経度の 2 か所。
  - PROJ を cgo で組み込まず、Go で実装する。シングルバイナリを保つため。
  - まず横メルカトル図法を実装する。平面直角座標系も UTM も横メルカトルなので、パラメータ違いで両方をまかなえる。海外の施設もまず UTM で受けられる。
  - EPSG コードから投影法とパラメータを引く表をバイナリに埋め込み、対応する座標系は必要に応じて足す（ランベルト正角円錐図法の Lambert-93 など）。
  - JGD2011・WGS84・ETRS89 などは楕円体がほぼ同じで差も cm 程度なので、同じ扱いにする。測地系の変換パラメータが要る座標系（英国の OSGB36 など）は後回しにし、未対応の EPSG コードは登録時にエラーにする。
- アセットの取り込みは元データの座標系で分かれる。
  - 施設と同じ投影座標系のデータ：原点を引くだけで合う。
  - SLAM などの任意座標のデータ：位置合わせの変換を手で与える。
  - 3D Tiles（地心座標系）：投影座標へ変換し、ジオイド高で高さを補正する。
- 3D Tiles の変換は登録時に 1 回だけ計算し、4×4 の行列としてアセットの系列に保存する。表示時はタイルセット全体に掛けるだけで、頂点ごとの投影計算はしない。
  1. タイルセットの中心を地心座標から緯度経度、施設の投影座標へ変換する
  2. その地点の東・北・上の向きと子午線収差（座標北と真北の角度差）から回転を作る
  3. 原点を引き、ジオイド高で高さを補正して 1 つの行列にまとめる

  地球の丸みを無視した剛体変換の近似で、誤差は中心から 500 m で 2 cm 程度。数 km 規模の敷地は範囲を分けて別の系列にする。

- 対応する順は、点群（Potree v2）、GLB、3D Tiles とする。ドローンメッシュがない顧客もいるので、3D Tiles を後回しにしても最初に届ける価値は変わらない。
- XY が緯度経度で Z がメートルのデータは扱わない。登録時に `metadata.json` などの範囲から度の値らしいものを検出してエラーにし、事前に投影座標へ変換するよう案内する。
- 計測値は投影座標上の距離で、縮尺係数（平面直角座標系では 0.9999 前後、UTM の中央子午線付近では 0.9996）の分だけ実距離とずれる（1 km あたり数十 cm 以内）。施設の範囲では実用上問題ないが、その旨を明記する。

## 空間の構造

- 施設の中は「施設 → 建屋 → 階 → エリア」のような木で表し、その要素をスペース（コードでは `Space`）と呼ぶ。施設・建屋・階・エリアのどれもスペースで、深さは任意。点群のオクツリーのノードとは別物。
- 座標は施設ローカル座標（[座標系](#座標系)）。すべてのデータは登録時にこの座標系へ合わせる。
- 建屋は外形（回転を含む矩形の組み合わせ。L 字形などにも対応）を持つ。
- 階は床の標高と天井の高さを持つ。天井を切る高さは階ごとの既定値（例：床から 2.5 m）を持ち、画面で調整できる。天井付近の配管やダクトを見せたいことがあるため。

## データの種類

データは次の 2 種類に分ける。

|              | 空間を構成するデータ       | 空間に置く要素                                             |
| ------------ | -------------------------- | ---------------------------------------------------------- |
| 例           | メッシュ、点群、3DGS       | 360°写真、注記                                             |
| 数           | スペースあたり少数         | エリア内にいくつでも                                       |
| 大きさ       | 大きい（ストリーミング）   | 小さい（1 件ずつ取得）                                     |
| 位置         | アセット全体の座標変換     | 1 件ごとの位置（写真は姿勢も）                             |
| 所属         | 付けたスペース             | 置いた位置のスペース（位置から自動判定し、手で変更できる） |
| 階の切り替え | クリッピングで空間ごと切る | 所属スペースで出し分ける                                   |

- 屋内・屋外とデータの種類は切り離し、どのスペースにもどの種類のアセットでも付けられる。屋外を点群で取る顧客もいる。
- どのデータ種別も必須にしない。ドローンメッシュがない施設では、建屋の外形を押し出した箱や、地面に貼った配置図・オルソ画像を屋外の手がかりにする。
- 計測・ピック・注記の配置は点群で行う。3DGS は見た目用で、正確な表面の位置を持たない。

## ファイル形式

| 種類     | 受け付ける形式                    | 配信形式                                  | 変換                                    |
| -------- | --------------------------------- | ----------------------------------------- | --------------------------------------- |
| メッシュ | 3TZ / 3D Tiles の ZIP / GLB       | 3TZ / GLB                                 | ZIP は登録時にサーバーで 3TZ に作り直す |
| 点群     | Potree v2（`DEFAULT` / `BROTLI`） | 同じ                                      | 外部で PotreeConverter                  |
| 3DGS     | SPZ / SOG / PLY / RAD             | RAD（Spark 2.0 の LoD 形式。分割しない）  | 外部で Spark の `build-lod`             |
| 360°写真 | equirectangular の JPEG           | JPEG のキューブマップ（1 面 512 と 2048） | Go のサーバー内で変換                   |

- 版のファイルはストレージ上で数個以下にする。Potree v2 は 3 つ、RAD・GLB・3TZ は 1 つ。
- 元ファイルと配信用のファイルが異なる場合（3D Tiles の ZIP、3DGS の変換前、360°写真）は両方を保存する。
- 3D Tiles は、数万のファイルからなることがあるため、3TZ（3D Tiles Archive Format。ZIP に、パスの MD5 とファイル位置の索引 `@3dtilesIndex1@` を付けた形式）で持つ。Metashape や ArcGIS Online は 3TZ を直接書き出せる。
  - 普通の ZIP は、登録時に索引を付けて 3TZ に作り直す。タイルの GLB はたいてい Draco や meshopt で圧縮済みなので、エントリは無圧縮にする。
  - 登録時に、索引が正しいこと、`tileset.json` からの参照がすべてアーカイブの中を指すことを検証する。外部への参照はエラーにする。
  - 3D Tiles は通常、地心座標系（ECEF）で書き出されるため、施設座標への変換をアセットの系列に持つ（[座標系](#座標系)）。狭い範囲なら GLB 1 ファイル（Draco / meshopt 圧縮）も受け付ける。
- 360°写真は JPEG にする。Go の標準ライブラリだけで変換でき、シングルバイナリを保てる。WebP は cgo が要り、KTX2 は写真の画質が粗くなるか、ファイルが大きくなる。
- 360°写真は 1 面 512 のプレビューを先に出し、2048 に差し替える。銘板の文字を拡大して読めるようにするため。完全なタイル化はしない。
- 360°写真は SLAM・TLS 付属のものも、Insta360 などで別に撮ったものも受け付ける。向きは方位角だけでなく回転（クォータニオン）で持つ。

## 配信

- 配信用のファイルはすべて、ブラウザがストレージから HTTP Range で直接読める形にする。配信時にサーバーで加工しない。サーバーの仕事は認可と URL の発行だけにし、後から S3 や Cloudflare（R2）から直接配信できるようにする。
- 認可は署名付き URL で行う。権限のない人には URL を発行しない。
  - S3 API の署名付き URL は S3・R2・MinIO で同じ実装で動き、署名が Range ヘッダーを含まないので、同じ URL に何度でも Range リクエストを出せる。版のファイルは 1〜3 個なので、ファイルごとの発行で足りる。
  - 有効期限は 1 時間程度にする。フロントエンドは取得に失敗したら API から URL を発行し直す。
  - 署名に使う時刻を時間帯（例：30 分単位）に丸め、同じ時間帯には同じ URL を返す。URL が変わるとブラウザのキャッシュが効かないため。
  - 発行済みの URL は取り消せないので、権限を外しても最大で有効期限の間はアクセスできる。
  - サーバーには「版のファイルの URL を発行する」処理を 1 つだけ置く。CDN のキャッシュが必要になったら、この処理を CloudFront の署名付き Cookie や Cloudflare のトークン検証に差し替える。フロントエンドとデータは変えない。
- OSS 版などローカルディスクで動かすときは、Go のサーバーがファイルを配信する。
  - URL は S3 と同じ形の署名付き URL にし、Go のサーバーが HMAC で署名・検証する。フロントエンドからはストレージの種類が区別できないようにする。
  - Range 付きで返すだけで加工しない（`http.ServeContent`）。
- 版のファイルは登録後に変わらないので、`Cache-Control: immutable` で長くキャッシュさせる。

| 形式      | ブラウザでの読み方                                                               |
| --------- | -------------------------------------------------------------------------------- |
| Potree v2 | `@geemil/potree-v2-three` が 3 ファイルを Range で読む                           |
| RAD / GLB | Spark・Three.js がそのまま読む                                                   |
| 3TZ       | 自作の 3TZ リーダー（3DTilesRendererJS のプラグイン）が索引を引いて Range で読む |
| 360°写真  | JPEG をそのまま読む                                                              |

- 3TZ リーダーはワークスペースのパッケージとして作る。末尾から索引の位置を求め、パスの MD5 で索引を二分探索し、該当範囲を取得して展開する。圧縮方式は無圧縮・Deflate（`DecompressionStream`）・Zstandard（`fzstd` など）のすべてに対応する。3TZ を直接読める既製のブラウザ向けライブラリはないため。3DTilesRendererJS のプラグインでファイルの取得を差し替えられるかは実装時に確認する。
- 直接配信の注意点
  - 署名付き URL は閲覧中に期限が切れるので、ライブラリの取得処理で期限切れを検出して URL を取り直す（Potree のライブラリは `fetch` を差し替えられる）。
  - S3 の署名付き URL はファイルごとに発行する。CloudFront の署名付き Cookie なら接頭辞の単位でまとめて許可できる。
  - 署名はユーザーごとに変わるので、CDN のキャッシュのキーから署名を除外する。
  - ストレージの CORS で Range ヘッダーを許可し、`Content-Range` を公開する。

## 時系列

- メッシュ・点群・3DGS は「系列」と「版」で持つ。例：「タービン建屋 屋内点群」系列の 2024.03 版と 2026.08 版。
- 版は丸ごと差し替える。一部を取り直したときは、アプリの外で元データを編集（該当部分を削除して取り直した点群を追加）し、結果を新しい版として丸ごと登録する。アプリは版同士の差分を扱わない。
- 登録した版は変更しない。過去の寸法を測れることに価値があるため、古い版も残す。古い版は安価なストレージ層へ移せるようにする。
- 座標変換は系列に持たせ、版ごとに上書きできるようにする。通常は同じ座標系で取り直すが、基準がずれた場合に備える。
- 360°写真も「写真セット」（系列）と「版」で持つ。版は写真一式のスナップショットで、新しい版は前の版を元に作り、取り直した写真を足し、古くなった写真を外して公開する。設備の周りだけ撮り直す場合も、撤去した設備の写真を外す場合も、そのまま表せる。
- 画面で表示時点を選ぶと、アセットの系列ごとの版・写真セットごとの版・外壁ボックスのセットが、それぞれその日以前で最新のものに切り替わる。既定は最新。系列ごとに取り直しの時期が違っても、その時点の状態を再現できる。
- 注記は既定で時点に関係なく全部表示し、時点での絞り込みは後から足す。注記の位置は施設座標で持つので、版が変わってもずれない。
- 比較の表示（左右分割・スワイプ・差分の色付け）は後から検討する。

## 階と外壁の表示

- 階の表示・非表示も、表示階より上の切り取りも、クリッピングで行う。データが建屋全体で 1 ファイルでも、階ごとに分かれていても同じ動きにする。
  - 点群：`@geemil/potree-v2-three` の `PotreeV2Clipping`。`hide-inside` のボックスを使い、`prune: true` なら消えるオクツリーのノードは取得もしない。
  - メッシュ：Three.js の `clippingPlanes` と `clipIntersection` で、1 つの箱の内側を消す。
- 外壁は建屋ごとに 3 段階で切り替える。表示階の切り替えとは独立させる。

  | モード     | 動作                                   | 向いている場面                   |
  | ---------- | -------------------------------------- | -------------------------------- |
  | 表示       | 外壁をすべて表示                       | 外観の確認                       |
  | 手前を隠す | カメラ側の壁だけを消す（ドールハウス） | 1 つの階を斜めから見る           |
  | 隠す       | 外壁をすべて消す                       | 小さな建屋の全階を横から一望する |

- 外壁ボックスは管理者が手動で作る（外形から初期配置を提案する）。データは一度作れば長く使い、自動生成では消えすぎや消え残りが出るため。視点に応じて切り替えるので `prune: false` にする。
- 外壁ボックスは建屋に「適用開始日付きのセット」として持たせ、点群・メッシュ・3DGS で共有する。新しい版を登録しても前のセットを引き継ぎ、外壁が変わったときだけ調整したセットを登録し直す。
- 斜め上から全階を見る分解図（階ごとに上下へ離す）は、点群を階の数だけ読み込むことになるので、必要になってから検討する。

## 編集モード

管理者向けに次の編集を用意する。

- 外壁ボックスの配置（移動・回転・伸縮、外側の向き、対象の階の範囲）
- 360°写真の位置合わせ
  1. 点群や俯瞰図で床をクリックし、カメラの高さを入れて位置を決める
  2. 撮影位置から見た点群を写真に半透明で重ね、回して輪郭を合わせる
  3. 精度が要るときは、写真と点群で対応する 3 点以上を指定して回転を求める（後から追加）

  同じ版で追加する 2 枚目以降は、前の写真の近くに仮置きして作業を速くする。

- 新しい写真を位置合わせしたとき、近く（例：水平 2 m 以内、同じ階）に前の版から引き継いだ写真があれば、「この版から外しますか？」と提案する。距離だけで自動では外さない。配管の両側から撮った写真のように、近くても両方残したい場合があるため。

## セキュリティ

- クリッピングは見た目の制御で、アクセス制御ではない。ファイルの URL が分かれば、隠した範囲の点も取得できる。
- 特定のユーザーにしか見せたくない範囲は、元データから削って別のファイルに分け、配信のたびに認可を確認する。
- 点群などは 1 回の表示で大量の Range リクエストを出すので、ストレージから直接配信するときは有効期限の短い署名付き URL を使う（[配信](#配信)）。CDN を挟むときは、認可済みの応答が別のユーザーに返らないようにする。
- スペース名、注記（コメント・添付ファイル）、写真、検索結果、ミニマップの外形、保存ビューのサムネイル、共有リンクも、権限のないユーザーにはサーバー側で返さない。
- 隣のエリアの写真や屋外メッシュへの写り込みは、運用で注意する。
- 権限はスペース（とその配下のデータ）単位で付ける（[権限](#権限)）。

## 関連リンク

- 注記の関連リンクは、注記ごとに URL を手で入力できる。
- テナントごとに、システム名と `{code}` を含む URL のテンプレートを登録できるようにする（後から対応）。注記の設備番号（`code`）を入れるだけで、設備台帳や点検履歴へのリンクを作れる。注記はすでに `code` を持つので、後から足しても既存のデータは困らない。

## 変更履歴

- 変更内容をすべて持つのではなく、操作を記録する。誰が・いつ・何に（種類と ID）・何をしたか（作成・更新・削除・権限変更など）と、短い要約（変更した項目名など）を残す。記録は追記のみで、変更しない。
- 注記の削除は論理削除にし、記録から辿れるようにする。誤って削除したときに戻すため。
- アセットは版として、コメントは追記として残るので、別に保存しない。
- この記録は画面の「最近の更新」の一覧に使う。実行者の名前は、ユーザーを削除しても分かるよう、その時点の値を記録に複製する。
- 監査ログとしての拡張は、最初に届ける価値ではないので後から足す。次を想定し、認可の判定を 1 か所にまとめておくことで後から差し込めるようにする。
  - アクセスの記録：ログイン（成功・失敗）、制限付きスペースの閲覧、添付ファイルや元データのダウンロード。点群は Range リクエストごとではなく、アセットを開いたことをセッションごとに 1 回記録する。
  - 管理操作の変更前後の値（権限・ユーザー・共有リンク・テナント設定）
  - IP アドレス、ユーザーエージェント、ゲストや共有リンクによる操作の識別
  - 改ざん防止（テナント管理者でも変更・削除できない）、保持期間、CSV の書き出し、SIEM への転送
  - SaaS で運用する場合の、運営側のサポート担当によるアクセスの記録

## データ構造

SQLite と PostgreSQL の両方で同じ形で動かす。主キーは UUIDv7。

### URL に出す ID

- テナントは `slug` で URL に出す（サブドメインか `/t/{slug}`）。OSS 版では出さない。
- 施設・注記・360°写真・保存ビュー・フォルダは、主キーとは別に URL 用の `public_id`（Base58 で 10 文字のランダム ID。テナント内で一意）を持つ。名前から作る slug にしないのは、日本語名と相性が悪く、名前を変えるとリンクが切れるため。
- フォルダの階層は URL に入れない。移動でリンクが切れ、権限のない人に組織の構造が見えるため。

### テナント・ユーザー・フォルダ・権限

```text
tenants        id, name, slug, created_at
users          id, tenant_id, email（テナント内で一意）, display_name, is_admin,
               status（active / disabled）, password_hash, created_at, last_login_at
groups         id, tenant_id, name
group_members  tenant_id, group_id, user_id
folders        id, tenant_id, public_id, parent_id（NULL はルートだけ。テナントに 1 つ）,
               name, sort_order, restricted, created_at, created_by
grants         id, tenant_id, user_id | group_id, folder_id | site_id | space_id,
               role（viewer / editor / manager）, expires_at, created_at, created_by
favorites      tenant_id, user_id, site_id, created_at
site_visits    tenant_id, user_id, site_id, last_opened_at
```

- 付与の相手と対象は、`resource_type` と `resource_id` の 2 列にせず、外部キーの列を分けて「どれか 1 つだけ」を CHECK 制約で保証する。参照の整合性を外部キーで守るため。
- 権限は、対象から「スペース → 施設 → フォルダ → ルート」と親へ遡り、本人と所属グループへの付与を集めて最も強い役割にする。`restricted` の所で遡りを止める。テナント管理者は判定を飛ばす。遡りは `WITH RECURSIVE` で書く。
- ユーザーは削除せず停止する。変更の記録で実行者を辿れるようにするため。
- ユーザーは複数のグループに属せる（`group_members` で多対多）。グループの入れ子は作らない。
- 最初はパスワードログインだけにする。SSO（SAML / OIDC）とグループの同期は後から対応する。その際、ログイン時の同期だけでは ID 基盤側の変更（退職・異動）がログインするまで反映されないので、ID 基盤から変更を送ってもらう SCIM を検討する。`sso_subject` は SSO の対応時に足す。

### 施設・スペース

```text
sites   id, tenant_id, public_id, folder_id, name, address, restricted,
        crs_kind（projected / local）, crs_epsg, origin_x, origin_y, origin_h,
        rotation_deg, geoid_height, created_at, created_by, updated_at
spaces  id, tenant_id, site_id, parent_id（NULL は施設の直下）,
        kind（outdoor / building / floor / area / other）, name, sort_order, restricted,
        bounds（min / max の 6 値）,
        footprint（建屋のみ。回転を含む矩形のリストを JSON で）,
        floor_elevation, floor_height, cut_height（階のみ）,
        created_at, created_by, updated_at
```

- 施設はスペースの木の外に置き、スペースは施設の下の木にする。施設は座標系と所属フォルダを持つ別の物で、権限を遡る順（スペース → 施設 → フォルダ）とも一致する。
- 建屋と階にしか使わない列は、NULL を許して同じテーブルに置く。外形の矩形は数が可変なので JSON で持つ。
- `kind` が効くのはアイコン、外壁ボックス、階の切り取りだけ。アセットや注記はどの種類のスペースにも付けられる。`other` はどの種類にも当たらない場所（配管ラックの一角など）に使う。
- 階の切り取りは、建屋の外形と、階の床の標高・次の階までの高さから計算する。
- すべてのスペースに範囲を持たせ、移動先や、注記・写真の所属の判定に使う。エリアや屋外は外形から範囲を計算できないため。

### アセット

```text
asset_series    id, tenant_id, site_id, space_id, kind（pointcloud / mesh / gsplat）, name,
                transform（施設座標への 4×4 行列）, display（表示の既定値の JSON）,
                created_at, created_by, updated_at
asset_versions  id, tenant_id, series_id, captured_on, source, note,
                format（potree2 / 3tz / glb / rad）, status（uploading / processing / ready / failed）,
                error, transform（版ごとの上書き。NULL なら系列の値）, storage_prefix,
                bounds（施設座標での範囲）, size_bytes, stats（点数などの JSON）,
                created_at, created_by
```

- ファイルは 1 行ずつ持たず、版ごとの接頭辞にまとめる。配信の入口のファイル名は形式で決まる（`metadata.json`、`tileset.3tz`、`scene.glb`、`scene.rad`）。

  ```text
  tenants/{tenant}/sites/{site}/assets/{series}/{version}/original/...   元ファイル（配信用と異なる場合）
  tenants/{tenant}/sites/{site}/assets/{series}/{version}/delivery/...   配信用ファイル
  ```

- 表示時点では、系列ごとに `status = ready` で `captured_on` が選んだ日以前のうち最新の版を選ぶ。登録日ではなく取得日で選ぶので、古いデータを後から登録しても正しい時点に入る。
- 変換は、3D Tiles に合わせてすべて行列で持つ。画面では平行移動と回転に分解して編集する。
- 版は登録後に変えない（`note` を除く）。誤って登録した版は、管理の権限を持つ人がファイルごと削除できる。
- 系列の `display` には、色の種類（RGB・強度・分類など）、点のサイズ、EDL の強さなどの既定値を持たせる。色の情報がない点群などで、閲覧者が毎回設定しなくて済むようにする。既定は RGB（色の情報がない点群だけ強度など）。
- アップロードは、ブラウザからストレージへ直接行う。S3 / R2 はマルチパートアップロードの各部分に署名付き URL を発行し、数 GB でも Go のサーバーを経由させず、中断後の再開もできるようにする。ローカルディスクでは Go のサーバーが分割アップロードを受ける。
- 登録時の検証と範囲の計算は、ファイル全体を読まずに Range で済ませる（Potree の `metadata.json`、3TZ の索引と `tileset.json`、RAD のヘッダー）。
- SaaS ではテナントごとの容量の上限を、版・360°写真・添付ファイルの `size_bytes` の合計で管理する。

### 360°写真

```text
panorama_sets                id, tenant_id, site_id, space_id, name, created_at, created_by
panorama_set_versions        id, tenant_id, set_id, name, captured_on, camera, note,
                             based_on_id（元にした版）, status（draft / published）,
                             created_at, created_by
panorama_set_version_photos  tenant_id, version_id, panorama_id
panoramas                    id, tenant_id, public_id, site_id, space_id, name, captured_at,
                             position（x, y, z）, rotation（クォータニオン x, y, z, w）,
                             status（uploading / processing / unplaced / ready / failed）,
                             storage_prefix, size_bytes, created_at, created_by
```

- 写真は一度だけ保存し、版からは参照する。新しい版を作るときにファイルをコピーしない。
- 表示時点では、写真セットごとに `published` で `captured_on` が選んだ日以前のうち最新の版の写真を表示する。`draft` の版は閲覧者に見えない。
- 写真セットを分けておくと、屋外と屋内などを別々の周期で撮り直せる。
- 位置合わせ前の写真（別に撮った写真）は `unplaced` で保存し、`space_id`・`position`・`rotation` を NULL にする。ビューアーには出さず、編集モードの「未配置の写真」から位置合わせをして `ready` にする。SLAM・TLS 付属の写真で位置と姿勢があれば、すぐに `ready` にする。
- `captured_at` は写真ごとの撮影日時（EXIF から。なければ版の日付）で、時刻順の並びや前後の移動に使う。
- 「この地点の過去の写真」は、過去の版から近い位置の写真を探して出す。
- 下書きの版の編集（写真の追加・位置合わせ・外す）は編集の権限で行い、公開は管理の権限に限る。公開すると閲覧者全員の見え方が変わるため。
- 公開済みの版から参照されている写真は削除できない。公開済みのデータは管理の権限を持つ人が承認したもので、過去の時点の表示を壊さないため。下書きの版にしか入っていない写真と、未配置の写真は削除できる。
- 写り込んだ人の顔や車のナンバーは、最初は事前に加工した写真をアップロードしてもらう運用で対応する。自動のぼかしは後から検討する。
- ファイルの構成

  ```text
  {prefix}/original.jpg            元の equirectangular（ダウンロード用）
  {prefix}/thumb.jpg               一覧用の小さな画像
  {prefix}/preview.jpg             1 面 512 の 6 面を 3×2 に並べた 1 枚（1536×1024）
  {prefix}/{px,nx,py,ny,pz,nz}.jpg 1 面 2048 の 6 枚
  ```

  プレビューは 1 回のリクエストで最初の表示ができるよう 1 枚にまとめる。高解像度は 1 枚にすると 6144×4096 になり、テクスチャの上限（4096）を超える端末があるので 6 枚に分ける。署名付き URL は、表示中の写真とその前後の分だけ発行する。

### 注記

```text
annotations             id, tenant_id, public_id, site_id, space_id,
                        category_id, code, title, description,
                        position（x, y, z）, extent（中心・大きさ・Z 軸回りの回転の JSON）,
                        view（カメラの位置と注視点の JSON）,
                        created_at, created_by, updated_at, updated_by, deleted_at, deleted_by
annotation_categories   id, tenant_id, name, icon, color, sort_order, archived_at
annotation_comments     id, tenant_id, annotation_id, author_id, body,
                        created_at, edited_at, deleted_at
annotation_links        id, tenant_id, annotation_id, title, system, url, sort_order,
                        created_at, created_by
annotation_attachments  id, tenant_id, annotation_id, name, mime_type, size_bytes, storage_key,
                        thumbnail_key, is_cover, status（uploading / ready）,
                        created_at, created_by
```

- `code`（設備番号）は、施設の中で一意にする（空欄は許す）。外部システムから設備を指す共通の鍵にするため（[将来の拡張](#将来の拡張)）。
- 注記の種類はテナントごとに定義する。種類自体には特別な意味を持たせない。
  - アイコンは、Lucide から注記に向いたもの（数十個）を用意して選んでもらう。色は、暗い 3D ビューの上で見分けやすいパレット（8 色程度）から選ぶ。画像のアップロードは受け付けない。どのテナントでも見た目がそろい、見づらい組み合わせを防ぐため。
  - 使われている種類は削除できず、`archived_at` で新しい注記では選べなくする。
  - テナントを作るときに「設備・メモ・要対応」を入れておく。定義するのはテナント管理者。
- 注記に状態（未対応 / 対応済みなど）は持たせない。対応の管理は外部システムで行い、関連リンクから辿ってもらう。対応済みになった注記は、種類を変えるか削除する。必要になったら、種類ごとの「状態を使う」設定と注記の状態の列を足す。
- 選択時に描く箱は、斜めに置かれた設備にも合うよう、中心・大きさ・回転で持つ。
- `view` には、注記を作ったときのカメラの位置と注視点を自動で保存する。付けた人は対象がよく見える位置からクリックしているため。「現在の視点で更新」で編集の権限を持つ人が直せる。「フォーカス」はこの視点へ移動する。
- 360°写真とは紐づけない。写真に対象が写っている保証がなく、写真の版が変わると維持も面倒なため。注記へ移動すれば近くの写真のマーカーが見えるので、そこから選んでもらう。
- 注記の内容を伝える画像は添付ファイルで付ける。画像（JPEG・PNG・WebP）はパネルの上部にギャラリーとして出し、1 枚を代表画像（`is_cover`）にしてピンや一覧のサムネイルに使う。今見ている 3D ビューや写真モードの画面を、画像として添付できるようにする。
- 添付ファイルの安全性
  - ダウンロードは `Content-Disposition: attachment` と `X-Content-Type-Options: nosniff` を付けて返す（S3 の署名付き URL では `response-content-disposition` で指定する）。利用者がアップロードした HTML や SVG をアプリと同じドメインで表示すると、スクリプトが動く危険があるため。
  - 画面に出すサムネイルは、ワーカーが元画像を読み直して JPEG で作り直したものにする。サーバーが作り直した画像なので、アプリと同じドメインから表示できる。
  - PDF などをブラウザ内で表示したくなったら、アプリとは別のドメインから配信する。
- 添付ファイル 1 つのサイズの上限は、テナントごとに設定できる（初期値は 100 MB 程度）。アップロードはアセットと同じく、署名付き URL でストレージへ直接行い、大きなファイルはマルチパートアップロードにする。SaaS では、添付ファイルもテナントの容量の上限に含める。
- 権限：閲覧はコメントまで、編集は注記・リンク・添付ファイルの作成と変更。コメントの編集と削除は本人と管理の権限を持つ人ができる。
- 注記の削除は論理削除にする（[変更履歴](#変更履歴)）。

### 外壁ボックス

```text
wall_box_sets  id, tenant_id, site_id, space_id（建屋）, effective_from, note,
               status（draft / published）, based_on_id, created_at, created_by
wall_boxes     id, tenant_id, set_id, center（x, y, z）, size（x, y, z）, rotation_z,
               outward_deg（外側の向き）, label
```

- 階の範囲は箱の高さで表す。1〜2F だけを覆う箱なら、その範囲の外壁だけが対象になる。
- 「手前を隠す」では、カメラが箱の外側の面より外にあるときに隠す。判定は毎フレーム、ブラウザで行う。
- 新しいセットは前のセットを元に作る。下書きの編集は編集の権限、公開は管理の権限で行う（写真の版と同じ）。

### 保存ビュー

```text
saved_views  id, tenant_id, public_id, site_id, name, camera（位置と注視点）,
             state（非表示のスペース、表示階、建屋ごとの外壁のモード、レイヤーの JSON）,
             as_of（表示時点。NULL は常に最新）, thumbnail_key,
             visibility（private / shared）, created_at, created_by
```

- 公開範囲は、自分だけ（`private`）と、施設を見られる人全員（`shared`）の 2 種類。共有の保存ビューを作れるのは編集の権限を持つ人。
- 表示時点は固定するか「常に最新」にするかを選べる。過去の寸法の確認に戻れるようにするため。
- 表示状態は、画面の機能が増えるたびに中身が増えるので JSON で持つ。削除されたスペースの ID は表示時に無視する。
- ログインしている人どうしの「ビューを共有」は、カメラや表示状態を URL に入れるだけで、テーブルは使わない。

### 共有リンク（後から足す）

```text
share_links  id, tenant_id, site_id, token_hash, space_id（見せる範囲）, view_id,
             expires_at, revoked_at, last_used_at, created_at, created_by
```

- アカウントのない人向けの閲覧専用リンク。最初は作らない。OSS 版は LAN 内で動かすことが多く、外部の人に見せる場面が少ないため。
- トークンはハッシュだけを保存し、DB が漏れてもリンクとして使えないようにする。
- 制限付きのスペースは、範囲の中にあっても見せない。

### 変更の記録

```text
activity_log  id, tenant_id, site_id, actor_id, actor_name, action, target_type, target_id,
              target_label, summary（変更した項目名などの JSON）, created_at
```

- 追記のみで、変更・削除しない。
- 実行者の名前と対象の名前は、その時点の値を複製する。ユーザーや対象が削除されても読めるようにするため。
- `site_id` で施設ごとの「最近の更新」を出す。

## バックグラウンド処理

- 写真のキューブマップへの変換、普通の ZIP から 3TZ への作り直し、登録時の検証などは、リクエストの中で行わず、DB のジョブ表に積んでワーカーが処理する。
- ワーカーは同じバイナリの別の動作モード（例：`spatialhub worker`）にする。
  - OSS 版では、サーバーのプロセスの中でワーカーも動かす。
  - AWS などでは、同じバイナリのコンテナを ECS のタスクとして別に動かす。
- ワーカーはファイルをストレージの共通のインターフェース（ローカルディスク / S3 / R2）で読み書きし、ローカルディスクは一時ファイルにだけ使う。どこで動いても同じ処理になるようにするため。
- ジョブは何度実行しても同じ結果になるようにし、処理中の印と期限（`locked_until`）を持たせて、ワーカーが落ちても別のワーカーがやり直せるようにする。PostgreSQL では `FOR UPDATE SKIP LOCKED` で複数のワーカーに配る。
- 将来 PotreeConverter や `build-lod` をアプリ側で動かす場合は、それらを入れたワーカーのコンテナで処理する。

## 将来の拡張

- 外部システム（IoT センサーの監視など）から API で、設備の位置に吹き出しを出す。「P-101A に異常」のように、注記の `code` で設備を指す。
  - 注記とは分け、一時的な表示（外部システムが消すか、期限が来れば消える）として扱う。異常の管理は外部システムが担い、このアプリは空間のどこで起きているかを見せる。
  - 外部システム用に、テナントごとのサービスアカウントと API キーを発行する。権限はユーザーと同じ付与の仕組みを使う。
  - 画面にすぐ出すため、サーバーからブラウザへの通知（Server-Sent Events など）を用意する。
